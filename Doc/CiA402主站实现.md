## 二、main.c 的接线

```c
canopen_app_init(&canOpenNodeSTM32);

co_master_init(canOpenNodeSTM32.canOpenStack, canOpenNodeSTM32.activeNodeID);
cia402_init(canOpenNodeSTM32.canOpenStack, CIA402_DEFAULT_NODE_ID);

while (1) {
    canopen_app_process();   /* 协议栈非实时部分：NMT / SDO 服务器 / 心跳 */
    co_master_poll();        /* 推进 SDO 事务（底层） */
    cia402_process();        /* 读事务结果，决定下一步（业务） */
}
```

**后两个的顺序不能颠倒**（`APP/main.c:232-238`）：`co_master_poll()` 负责
把事务往前推，`cia402_process()` 只看事务的结果。先让底层跑完，状态机这
一轮就能立刻看到结果，少等一个主循环周期。

第二、三个调用必须**等 `canopen_app_init()` 成功之后**——它内部才创建
`canOpenStack`。

**本机节点号只传给 `co_master_init`，不从 `cia402_init` 里传**：本机节点号
是协议栈的配置，属于底层的事；`cia402` 只关心「要对哪个从站做什么」。
早先版本让 `cia402_init` 硬编码 0 代进去调 `co_master_init`，结果「SDO
目标不能是自己」这个保护形同虚设（注释还写着它在起作用），已改掉。

## 三、canopen_master：SDO 客户端事务层

### 3.1 上游是非阻塞的，这一层必须也是

SDO 报文的**接收**在 CAN 中断里完成（`CO_SDOclient_receive` 是注册给驱动
的回调），但**状态推进**要靠调用者周期性地调 `CO_SDOclientUpload()` /
`Download()`。

所以这里**不能**做成 `co_master_read(...)` 这种阻塞函数：一死等，主循环就
停了，`canopen_app_process()` 不再执行 —— NMT、SDO 服务器、心跳全部停摆，
事务反而等不到结果。必须拆成「发起 → 轮询 → 取结果」三段。

对外的用法：

```c
co_master_start_read(2, 0x1000, 0, 1000);   /* 发起，立刻返回 */
...                                        /* 期间继续跑主循环 */
if (!co_master_busy()) {                   /* 事务结束了 */
    if (co_master_get_result() == CO_MASTER_OK) {
        uint32_t v; co_master_get_u32(&v);
    }
}
```

同一时刻只允许一次事务，`busy` 期间再调 `start_*` 直接返回 `false`。

### 3.2 几个必须知道的实现点

**① `CO_SDOclient_setup()` 不会被跳过**（`canopen_master.c:81`）

本工程 `CO_CONFIG_SDO_CLI = 0x03`（`ENABLE | SEGMENTED`），**没有**
`CO_CONFIG_FLAG_OD_DYNAMIC`。因此 `CO_SDOclient_setup()` 里那道「参数没变
就 early-return」的优化**不生效**，每次调用都会真的重新登记 CAN 收/发缓冲。

这正是需要的：多轴之间换目标节点时，不会残留上一轴的接收缓冲。顺带也说明
**对象 0x1280 不用配** —— 那个条目只在开 `OD_DYNAMIC` 时才会被读取。

**② `CO_SDOclientClose()` 是真的关接收**（`canopen_master.c:43-52`）

它只把 `state` 置回 `CO_SDO_ST_IDLE`，看着像没干什么。但上游的
`CO_SDOclient_receive()` 开头就判 `state != CO_SDO_ST_IDLE` 才收报文——
所以这一步确实切断了该 SDO 通道的接收，避免事务结束后还有迟到的报文写进缓冲。

**③ `co_master_poll()` 里的 1ms 节流是必需的**（`canopen_master.c:159-172`）

SDO 的超时计时器是**按两次调用传入的时间差累加**的。如果同一毫秒内被反复
调用（主循环空转时完全可能），传进去的 `timeDifference_us` 恒为 0，从站不
应答时就**永远等不到超时**，事务卡死。节流保证每次至少推进 1ms。

**④ `CO_SDO_RT_uploadDataBufferFull` 要单独处理**（`canopen_master.c:185-193`）

分段读长对象时 FIFO 会满，此时返回值是特殊值 `5`（不是普通的「进行中」）。
必须先 `UploadBufRead` 把数据取走，否则下一轮还是这个返回值，永远卡住。
取干净后直接 `return`，下一轮继续推进。

结果缓冲区 `CO_MASTER_MAX_DATA = 32` 字节，与客户端内部 FIFO 同量级，够读
`0x1018` 这种 4×4 字节的数组；更长的对象（错误历史 0x1003、字符串）本模块
不支持，会以 `CO_MASTER_ERR_ARG` 收场 —— 这是**能力上限，不是通信故障**。

**⑤ abort 码映射**

`CO_SDOclientUpload/Download` 返回负数时，`abortCode` 已经填好了。这里把
`CO_SDO_AB_TIMEOUT (0x05040000)` 单独映射成 `CO_MASTER_ERR_TIMEOUT`，
其余一律 `CO_MASTER_ERR_ABORT`。两者的区别在调试时很关键：

| abort 码 | 含义 | 说明 |
| --- | --- | --- |
| `0x05040000` | SDO 协议超时 | 帧发出去了，从站一个字节都没回 |
| `0x08000000` | 通用错误 | 从站**在**，明确拒绝 |
| `0x06010000` | 不支持该对象访问 | 从站在，但这个对象读不了 |

### 3.3 发起失败不再静默（`co_master_start_err_t`）

`co_master_start_*` 返回 `false` 有好几种原因，早先版本**一律不吭声**。
后果很严重：上层状态机在 `STEP_*_START` 里发现没发起成功，`return` 掉，
下一轮再来，于是**以主循环的速度空转** —— 既不发报文也不打日志，看起来
跟死机一模一样。

现在有了 `co_master_get_start_error()` + `co_master_start_error_name()`：

| 枚举 | 含义 |
| --- | --- |
| `CO_MASTER_START_NOT_INIT` | `co_master_init` 没调，协议栈没起来 |
| `CO_MASTER_START_BUSY` | 上一次事务还没结束（**正常情况**，不必报错） |
| `CO_MASTER_START_BAD_NODE` | 节点号非法，或**等于本机节点号** |
| `CO_MASTER_START_SETUP_FAIL` | CAN 缓冲区登记不上 |
| `CO_MASTER_START_INITIATE_FAIL` | SDO 客户端拒绝发起 |

「节点号等于本机」这条是特意拦的：本工程的 bxCAN **没开回环**（见
`can.c` 的 `MX_CAN1_Init`），自己发的帧自己收不到，SDO 请求发到自己头上
只会空等到超时。宁可当场失败也不要空转。

## 四、cia402：使能状态机

### 4.1 为什么是闭环而不是盲发控制字

CiA 402 的使能**不是一个可以盲发一串控制字的开环流程**：驱动器当前在哪个
状态，决定了下一步该发什么命令，而状态**只体现在 0x6041 里**。

所以循环是：

```
读 0x6041 ─▶ 解码状态 ─▶ 按状态选控制字 ─▶ 写 0x6040 ─▶ 等 50ms ─┐
   ▲                                                              │
   └──────────────────────────────────────────────────────────────┘
   │ 直到解出 Operation Enabled
   ▼
每 1s 读一次 0x1000 并 printf
```

驱动器中途报警、掉使能、被别的节点改了状态，这个循环都能自己纠正回来。

### 4.2 状态字解码：顺序是个陷阱（`cia402.c:222-252`）

```c
if ((statusword & 0x4FU) == 0x00U) return CIA402_SW_NOT_READY_TO_SWITCH_ON;
if ((statusword & 0x4FU) == 0x40U) return CIA402_SW_SWITCH_ON_DISABLED;
if ((statusword & 0x6FU) == 0x21U) return CIA402_SW_READY_TO_SWITCH_ON;
if ((statusword & 0x6FU) == 0x23U) return CIA402_SW_SWITCHED_ON;
if ((statusword & 0x6FU) == 0x27U) return CIA402_SW_OPERATION_ENABLED;
if ((statusword & 0x6FU) == 0x07U) return CIA402_SW_QUICK_STOP_ACTIVE;
if ((statusword & 0x4FU) == 0x0FU) return CIA402_SW_FAULT_REACTION_ACTIVE;
if ((statusword & 0x4FU) == 0x08U) return CIA402_SW_FAULT;
return CIA402_SW_UNKNOWN;
```

`0x4F` 掩住 bit0~3 与 bit6；`0x6F` 多掩住 bit5。

**这个顺序是规范规定的，不能改。** 特征位越多的状态掩码越严，必须排在前面。
一旦调换 —— 比如把 `0x27`(Operation enabled) 挪到 `0x07`(Quick stop active)
后面 —— Quick stop active 会先被 `0x27` 那条命中，状态判断全乱。

解码函数**对外暴露**（`cia402_decode_statusword`）就是为了能单独测。已用
host `gcc` 跑了 16 组用例（8 个规范最小值 + 7 个真实驱动器常见值 + 1 组重复），全过。

### 4.3 控制字选择与「过渡态不写」

| 解出的状态 | 写 0x6040 |
| --- | --- |
| Switch on disabled | `0x0006` Shutdown |
| Ready to switch on | `0x0007` Switch on |
| Switched on / Quick stop active | `0x000F` Enable operation |
| Fault | `0x0080` ← 需 bit7 上升沿，见下 |

**过渡态不写控制字**：Not ready to switch on、Fault reaction active、Unknown
这三种状态下，驱动器正在自己往下一个状态走，写什么都不会被接受。代码直接
`arm(50ms) → STEP_SETTLE`，等一会儿重读状态字（`cia402.c:330-339`）。

**同值不重写**（`cia402.c:344-348`）：算出来的控制字和上次写下去的一样，
说明状态没往前走。重复写同一个值不改变什么，只会刷屏总线 —— 退化成
「等一会再读」，让 5 秒总超时去兜底。

### 4.4 故障复位靠边沿，所以要交替写（`cia402.c:302-311`）

故障复位由控制字 **bit7 的 0→1 边沿**触发。如果上一次已经发过 `0x0080`，
必须先写回 `0x0000` 把 bit7 拉低 —— 否则这次再写 `0x0080` 没有上升沿，
驱动器根本不会理。所以代码在两个值之间交替：

```c
if ((s_lastControlword & CIA402_CW_FAULT_RESET) != 0U)
    s_nextControlword = CIA402_CW_DISABLE_VOLTAGE;   /* 先把 bit7 拉低 */
else
    s_nextControlword = CIA402_CW_FAULT_RESET;       /* 再给上升沿 */
```

最多试 `FAULT_RESET_MAX_TRIES (3)` 次，仍无效则停在 `STEP_FAULT` ——
**这是整个模块唯一的终态**，因为「驱动器报了故障且复位不掉」确实需要人工处理。

### 4.5 重试分两层

这是 bring-up 阶段最关键的修正，详见第五节。

```
单次 SDO 失败
   │
   ├─ 本轮内还有配额（< SDO_MAX_IN_ATTEMPT = 3）？
   │     是 ─▶ 打一行，歇 50ms，重新读状态字 ── 继续
   │     否 ─▼
   └─ 整轮失败 ─▶ 打一行（含 abort 码），歇 ATTEMPT_RETRY_DELAY_MS = 2000ms
                  ─▶ 回 STEP_IDLE，重新发 NMT，从头来过 ── 永远重试
```

单帧丢失是正常的（总线有干扰、驱动器忙），一失败就从头来过会让状态机永远
收敛不了，所以先在本轮里重试；连续 3 次才判定这一轮没戏。

而整轮失败后**只退避 2 秒，不放弃** —— 驱动器晚上电、线没插好、上位机没
打开，这些都不是「今天不会再好」的错误。

## 五、bring-up 中发现并修掉的问题

### 5.1 【严重】状态机 5 秒后永久放弃

原实现里 `ENABLE_TIMEOUT_MS (5000)` 超时 → `CIA402_STATE_ERROR`，而且是
**终态，不再重试**。

任何一次失败（驱动器还没上电、线没插、PCAN-View 没开）都会让它从此闭嘴。
后果是**总线上安静得完全看不出发生过什么** —— 既没有错误报文，也没有重试
报文，只能靠翻串口日志才知道它早就停了。

改成失败后退避重试（`ATTEMPT_RETRY_DELAY_MS`，`cia402.c:40`），驱动器什么时候
上线什么时候自动接上。`CIA402_STATE_ERROR` 对外的含义也修正为「本轮没成功，
会自动重试」，不再是「结束」。

### 5.2 发起失败静默

见 3.3。修法是 `try_start()` 包装（`cia402.c:141-150`）：`CO_MASTER_START_BUSY`
当作正常情况直接返回，其余原因一律计入失败次数并打印出来。

### 5.3 `STEP_DEV_START` 空转

加过一个 `STEP_DEV_START` 步骤，但它什么也不做、立刻跳 `STEP_DEV_WAIT`。
删掉，让 `STEP_ENABLED` 直接发起读并转入 `STEP_DEV_WAIT`。

### 5.4 EMCY 分不清发送侧还是接收侧

CANopenNode 把「发送错误计数超限」和「接收错误计数超限」**合并成同一个错误位**
`CO_EM_CAN_BUS_WARNING (0x01)`（`301/CO_Emergency.h:182`）。收到这条 EMCY
只知道「计数器越过 96 了」，分不出是哪种，而这两种的排查方向完全相反。

但 `CANerrorStatus` 里收发两侧是**分开**的（`CO_driver.h:439-445`）。所以
`report_bus_status()`（`cia402.c:161-198`）直接读它，只在变化时打印：

```
CiA402: CAN 总线异常 0x0101: 发送报警 接收报警
CiA402: → 本机在发但无人应答：检查从站供电、接线、两边波特率
```

判读方法：

| `CANerrorStatus` | 含义 |
| --- | --- |
| 只有 `ERRTX_*` | 帧发出去了但**没人 ACK** —— 从站不在 / 未上电 / 波特率不对 / 线接错 |
| 也有 `ERRRX_*` | 总线上有**错误帧** —— 多半是两边波特率不一致 |
| 一直是 0 | 总线电气没问题，从站**收到了但不肯回**（对象不支持、状态机拒绝等） |

底层来源：`port/CO_driver_STM32.c:494` 读 STM32 的 `ESR` 寄存器
（`CAN_ESR_BOFF | CAN_ESR_EPVF | CAN_ESR_EWGF`）后填入。

## 六、实测：拿到的那两帧

用 PCAN-View 抓到的原始记录：

```
ID=129, Type=D, Length=8, Data=00000001
ID=1793, Type=D, Length=1, Data=05
```

**两帧都是本机（节点 1）自己发的，从站（节点 2）一个字都没说。**

### 0x701 / DLC=1 / `05` —— 心跳

节点 1 的启动后心跳，`05` = Operational。主站协议栈本身是正常的。✅

### 0x081 / DLC=8 / `00 00 00 01` —— EMCY

CANopenNode 的 EMCY 字节布局（`301/CO_Emergency.c:291-293`：前两字节是
`errorCode`，`data[2]` 是 `errorRegister`，`data[3]` 是 `errorBit`）：

| 字节 | 值 | 含义 |
| --- | --- | --- |
| 0–1 | `0x0000` | `CO_EMC_NO_ERROR` |
| 2 | `0x00` | 错误寄存器 0x1001 = 0 |
| 3 | `0x01` | `CO_EM_CAN_BUS_WARNING` |

**意思：CAN 控制器的错误计数器越过了 96 的警戒线。**

注意 `CO_EM_CAN_BUS_WARNING` 在上报和清除时用的都是 `CO_EMC_NO_ERROR`，
所以**同一个字节序列在「越线」和「恢复」时都会出现**。

发送错误计数器（TEC）每发一个没人 ACK 的帧 **+8**，所以这条 EMCY 说明
**至少 12 帧发出去没被确认**。

### 关键的是没收到的东西

**`0x602`（SDO 请求）一帧都没有。** 而状态机每 5 秒至少该发一串读 `0x6041`
的报文。一帧都没有，只有两种解释：

1. **它早就跑完一轮、失败、然后永久停住了** —— 即 5.1 那个 bug。若 PCAN-View
   是在板子启动之后才接上的，就完全对得上。
2. **`canopen_app_init()` 失败**。这里要分两种情况，结果不一样：

   | 失败点 | `canOpenStack` | `cia402_process()` 的行为 |
   | --- | --- | --- |
   | `CO_new()` 失败 | 保持 `NULL` | 第一行 `if (s_co == NULL) return;` **静默退出**，什么都不打 |
   | `resetCommunication()` 失败（返回 2~5） | **非 NULL**（在调用它之前就赋值了，见 `canopen_app.c:55`） | 照常运行，但 CAN 还在配置模式没上线，SDO 一路超时 |

   第二种情况下日志会自带 `CANopen: CO_CANinit failed: N` 之类的行，好认；
   第一种只剩一句 `CANopen: CO_new failed`，然后状态机全程无声。

**必须看串口日志才能区分**，PCAN-View 看不到这个。判断方法很简单：
日志里**有没有** `CANopen: node 1 up` 这一行 —— 有就是协议栈起来了。

## 七、bring-up 检查清单

板子上的固化行为（代码里读得到）：

- 节点号 `CIA402_DEFAULT_NODE_ID = 2`，波特率 500 kbit/s

需要在**驱动器上**确认：

| 项 | 要求 |
| --- | --- |
| SW1~SW5 | 低 5 位节点地址 = 2。**全 on 是广播地址，不能用** |
| SW6 / SW7 | `on` / `off` = 500 kbit/s。**出厂默认 `off`/`off` = 1 MHz** |
| SW8 | 只有总线最末端那台拨到 `on`（终端电阻） |
| 上电 | 改完拨码**必须重新上电**才生效 |

另外：CAN_H / CAN_L 别接反；驱动器要单独供电。

**波特率或节点地址对不上，完全符合「帧发出去没人 ACK、错误计数器涨过 96」
这个现象。**

### 串口日志该长什么样

新固件启动后大致会打这些：

```
Hello world :CANopenNode STM32F4xx Demo!
CANopen: allocated ... bytes for stack objects
CANopen: node 1 up
CiA402: 目标从站 = 节点 2，500 kbit/s（驱动器 SW6/SW7 需同为 500 kbit/s）
CiA402: 第 1 轮 —— 节点 2 ← NMT Start Remote Node
CiA402: 状态字 0x0040 → Switch on disabled
CiA402: 状态字 0x0021 → Ready to switch on
...
CiA402: 节点 2 已进入 Operation Enabled（用时 187 ms）
CiA402: [1234 ms] 节点 2 设备类型 = 0x00020192（profile = 402，type = 2）
```

失败时：

```
CiA402: CAN 总线异常 0x0001: 发送报警
CiA402: → 本机在发但无人应答：检查从站供电、接线、两边波特率
CiA402: 读状态字 0x6041 失败（本轮第 1 次，继续重试）
CiA402: 第 1 轮失败 —— 读状态字 0x6041 失败（结果=超时, abort=0x05040000）；2000 ms 后重试
```

那行 `abort=` 是分诊的关键 —— 见 3.2 ⑤ 的对照表：
`0x05040000` 是从站没回，`0x08000000` 是从站明确拒绝。

## 九、还没做的

- **总线上没验证过** —— 手上没有硬件，只做过编译和状态字解码的 host 测试。
- `0x1000` 只在进入 Operation Enabled 之后才开始读。按需求是这么定的，
  但 bring-up 阶段**先读一次 `0x1000` 再使能**会更有用 —— 那样不用等使能
  成功就能确认 SDO 通道是通的。
- 现在每步一次 SDO。正常跑起来应该换成 **RPDO/TPDO 周期映射**
  （控制字走 RPDO、状态字走 TPDO），SDO 只留给配置和偶发读写。
- 位置/速度/回零模式还没做：`0x6060`（模式）+ `0x607A`/`0x60FF`/`0x6098`。
- 多轴管理：轴号分配、NMT 状态编排、心跳超时处理。
